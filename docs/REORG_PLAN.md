## Verdict: a move, not a rewrite
- Lean declaration names do not depend on file paths; the library uses one flat `namespace NLAlib`
  (438 of 602 files; the rest are proof-local namespaces). No theorem, proof or name changes.
- What changes: file paths (`git mv`), `import` lines (rewritten from one old→new table),
  aggregator files (one per directory, regenerated), `scripts/check_layers.py`'s layer map
  (new top-level dirs Probability and RandomMatrix), the atlas areas' `module` fields (viewer
  boxes), docs that name paths (STANDARDS §2, AGENTS, README, CONTRIBUTING, briefs). The
  `module` field on formalizations is regenerated by the sync.
- Verification is mechanical: full `lake build`, extractor, sync, check_layers, check_atlas.

## Effort
1. Mapping table old path → new path (`docs/reorg/mapping.json`): ~250 individual decisions after
   the wholesale moves (SparseFock, Concentration/Matrix subtrees, InverseMoments, Factorizations);
   an agent drafts it from file names and module docstrings, Tyler reviews the flagged ~40.
2. `scripts/reorg.py`: applies the table (`git mv`), rewrites imports, regenerates aggregators and
   the layer map, updates atlas area modules. Minutes.
3. Full build + checks: ~10 minutes. Expected failures: none from Lean (names unchanged); possible
   import cycles if a file is placed below something it imports — the script checks the table
   against the import graph before moving anything.
4. Docs and briefs: path references; the atlas area tree should become the directory tree.
Estimated: one agent round (one day of agent time) plus a review pass. Not a rewrite.

## Risks and sequencing
- The move is one enormous diff. Any concurrent branch (codex) will conflict on every touched file;
  do it right after a merge of main, announce a freeze, and have other branches rebase onto it
  (git follows `git mv` renames, so rebases mostly succeed; edits to moved files need manual care).
- Files over 500 lines and "helpers in the wrong file" (ROUND8/9 followups) are a separate
  housekeeping pass; do not mix content moves into the path move, or the diff stops being
  mechanically verifiable.
- Porting to a new repo is orthogonal: push the reorganised history to the new remote (history
  preserved) or start fresh from the tree. Reorganise first, in this repo, so the move is verified
  by CI before the port.
